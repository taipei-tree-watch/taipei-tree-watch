- **repo**：`taipei-tree-watch`
- **中文名**：台北樹木觀測 / 台北市病樹地圖
- **域名**：待定，先查 `taipeitreewatch.org`、`treewatch.tw` 是否可用

## 1. 目的

建立一個公民回報的地圖網站，蒐集台北市**罹病與被移除的樹木**位置，
**核心目標是找出褐根病（Phellinus noxius）的空間熱點**，希望對防治有幫助。

這個目的必須貫串所有設計決策。這不是一個「樹木紀錄網站」，
而是一個**疫情地圖**。以下幾點都是從這個目的推導出來的。

### 為什麼熱點圖有價值

褐根病是土壤傳播的真菌病害，主要透過**根系接觸**與**病土、病根殘體移動**擴散。
病死樹的殘根可在土中存活多年，持續作為感染源。
因此疫情高度**空間聚集**——同一路段、同一公園、同一校園的樹木會接續死亡。

現況是各單位（公園處、學校、里長、住戶）各自處理，沒有跨單位的空間視角。
一張公開的點位圖可以讓「這條街三年內死了七棵」這種模式浮現出來。

### 這個目的帶來的四個非顯而易見的設計要求

**(1) 病因必須有憑據，不要讓回報者自己判斷**

一般人無法、也不該判斷一棵樹為什麼生病或被移除。所以證據標準很簡單：

**以現場的移除公告為準。** 台北市樹木移除前通常會張貼公告，上面會寫明原因。
有公告就照抄上面寫的；沒有公告就把病因留空，不要推測。

這條規則讓專案的性質改變，而且是往好的方向：

- 資料變成「官方自己說的」，不需要任何專業判斷就能達到高可信度
- 熱點圖上標為褐根病的點有文件依據，拿去跟公部門或里鄰溝通站得住腳
- 迴避了法律與爭議風險（見第 8 節）

代價是資料量會變少——很多樹是默默被移除的，或等有人注意到時公告早就撤了。
所以**必須允許「樹不見了但沒有公告」這種回報**：病因留空，點位照樣收。
而且要注意：大量沒有公告的移除聚集在同一區，本身就是值得注意的訊號，
不要把這類回報當成次等資料。

**(2) 照片連結的用途是存證**

`link` 欄位（Threads / IG / X 等貼文網址）是這個專案的核心，因為現場會消失——
公告會被撤掉、樹會被移走、樹穴會被填平，但網路貼文會留著。

引導使用者拍**三類照片**，都重要，而且可以放在同一篇貼文裡：

| 拍什麼 | 支持哪個欄位 |
|---|---|
| **移除公告** | 病因。這是唯一能決定病因欄位的憑據 |
| **樹木本體**（含樹幹基部、露出的根部、樹冠狀況） | 現況記錄。罹病或衰弱的樣貌、移除前後的對照 |
| **樹穴與殘株** | 處置。殘根還在不在、是否已水泥填平，只有這類照片看得出來 |

請注意這個分工：照片是用來**佐證使用者填的欄位**，不是用來讓使用者
從照片上自行判斷病因。病因永遠只看公告，見 (1)。

實務上很多情況只拍得到其中一類（例如發現時樹已經沒了，只剩樹穴），
這完全沒問題，UI 不要把附照片做成必填或多階段流程。

**(3) 殘根的去留有防疫意義**

使用者列的處置 tag（僅剩根部 / 連根移除 / 樹穴水泥填平）看起來像流水帳，
但在褐根病的脈絡下是關鍵資訊：**殘根留在原地 = 感染源留在原地**。
「已移除但殘根未清」的點應該被標示為持續風險，而不是結案。

**(4) 定位精度比一般回報地圖更重要**

熱點分析靠的是空間鄰近性。手機 GPS 在台北市區誤差 10–30 公尺，
足以讓相鄰兩棵樹的相對關係錯亂。選點 UX 必須處理這件事（見第 6 節）。

## 2. 範圍與非目標

**做**
- 匿名回報、免審核、直接上線
- 地圖呈現 + tag 篩選
- 受保護樹木參考圖層（pre-seed）
- Turnstile 防機器人 + 連結網域白名單 + 我自己的軟刪除後門

**不做（第一版）**
- 使用者登入
- 審核流程
- 檢舉、重複回報合併、狀態更新機制 —— 保留資料模型的擴充空間，但先不實作
- IP 限流 —— 熱心回報者不該被擋，真的遇到惡意流量再處理
- 圖片上傳與託管 —— 一律走外部連結

**地理範圍**：不需要嚴格的行政區界。一個寬鬆方框即可——
跑到新北照樣收，跑到新竹才拒絕。不要為此引入行政區 polygon 與 point-in-polygon 判斷。

## 3. 資料模型方向

分成兩張**性質完全不同**的表，不要混在一起：

### `trees` — 參考圖層（唯讀）

來源：台北市資料大平臺的「臺北市受保護樹木」資料集（提供機關為文化局，
含樹木編號、樹種、胸徑、地址、經緯度等）。請自行確認目前的資料集 ID 與欄位。

**這些樹並不是病樹**。它們是老樹、大樹，是褐根病最重要的受害對象，
所以作為底圖參考有價值——但絕對不能 pre-seed 進回報表，
否則一上線就有幾千個假的「病樹」點，整個資料集失去意義。

視覺上應與回報點明確區分（例如灰色小點 vs 彩色標記）。
回報時若位置貼近某棵受保護樹木，應提示使用者關聯過去
（「這棵受保護樹木被移除了」是這個網站最有價值的一類回報）。

### `reports` — 使用者回報

欄位意圖（不是最終 schema，請自行設計）：

| 欄位 | 用途 |
|---|---|
| 座標 | 精度到小數第 5 位就夠（約 1 公尺） |
| 樹種 | **自由填寫文字**，不做 tag。可提供 autocomplete 建議清單輔助，但不限制輸入 |
| 病因 tag | 多選。**僅在有公告或官方文件憑據時填寫**，無憑據留空 |
| 處置 tag | 多選 |
| 證據來源 | 單選，見第 1 節 (1) |
| 說明 | 自由文字，上限約 300 字。可用來照抄公告全文 |
| 連結 | 單一 URL，網域白名單 |
| 發現日期 | **可選，且與回報時間分開**。使用者常在事後才回報，擴散分析需要的是發現時間 |
| 關聯受保護樹木 | 可選，指向 `trees` |
| 狀態 | 供軟刪除使用 |
| 回報者識別 | IP 雜湊（加 salt，不存原始 IP）。不用來限流，只在遇到惡意流量時備用 |

### Tag 方向

三個維度，不要混成一組：

- **病因**（多選）：褐根病、其他病蟲害、枯朽、不明，以及**非病害原因**——
  捷運工程、道路工程、建築工程、防颱。
  非病害原因也要收，因為工程移除本身會移動病土、造成根系損傷，是褐根病的風險因子。
  選項的措辭應盡量貼近實際公告上的用語，讓使用者可以直接對照著選。

- **處置**（多選）：僅修枝葉、僅剩主幹、僅剩根部、連根移除、樹穴水泥填平、原地保留。
  注意第 1 節 (3) 的防疫含義：殘根留在原地就是感染源留在原地。
  這一組的憑據是樹穴與殘株照片，見第 1 節 (2)。

- **證據來源**（單選）：
  現場公告（有拍到照片）/ 現場公告（沒拍到）/ 新聞或官方文件 / 無公告，僅目擊。
  這一項取代了原本的「診斷可信度」，理由見第 1 節 (1)。
  病因 tag 應該只在有憑據時填寫；「無公告，僅目擊」的回報預設病因留空。

tag 清單要放在**單一 source of truth 檔案**，前後端共用。
內部編號只能新增、永不重排或回收，否則舊資料的語意會錯亂。

## 4. 技術方向

「免費、方便、不要因為沒流量就被停用」是選型的唯一標準。
建議 Cloudflare 全家桶（Pages + Workers + D1 + R2 + Turnstile），
理由是一個帳號搞定全部、免費額度夠用、且不會因閒置被暫停
（Supabase 免費專案閒置一週會被暫停並需要冷啟動，不適合初期沒流量的公開站）。

若你評估後有更好的組合，提出來討論。

地圖前端建議 MapLibre GL JS（避開 Google Maps 計費）+ client-side clustering。
圖磚來源請自行研究免費方案；台北市範圍很小，自架 tile 檔的成本趨近於零。

### 一個必須遵守的架構原則：讀寫分離

不要讓使用者的讀取請求直接打資料庫。

```
寫入：使用者 → Worker（驗證）→ DB
讀取：Cron → DB 全表 dump → 產生靜態快照檔 → 物件儲存 / CDN
      使用者 → 直接讀快照檔，完全不碰 DB
```

**「Worker」** 指 Cloudflare Workers，也就是跑在邊緣節點的 serverless function。
在這個架構裡它是唯一的後端，只有兩支：一支處理寫入請求，一支跑定時快照。
沒有常駐伺服器、沒有容器、沒有部署主機要顧。

**「驗證」** 指寫入前必須在伺服器端做完的檢查，至少包含：

- Turnstile token 驗證（向 Cloudflare 驗，不是只看前端有沒有過）
- 座標落在寬鬆方框內（見第 2 節）
- `link` 的網域在白名單內，且是合法 URL
- 說明欄位剝除所有 URL、限制長度
- tag 值在合法範圍內
- 產生回報者識別用的 IP 雜湊

**這些檢查全部要在 Worker 做，前端的同等檢查只算 UX 輔助。**
前端驗證是為了讓使用者即時看到錯誤，不構成任何防護——
任何人都可以直接對 API 發請求，繞過整個網頁。

這件事講明是因為前端已經會做座標範圍與網域白名單的檢查，
容易讓人覺得後端重做一次是多餘的。不是多餘，是唯一真正生效的那一層。

理由：
- 資料量小（預估上限一萬點），全量快照壓縮後只有幾百 KB，一次載入即可
- D1 免費額度是按「引擎掃過的列數」計算，且自 2026/9 起超額查詢直接失敗；
  讀取走靜態檔可以讓這個風險趨近於零
- 資料庫額度用光時，網站還是看得到

快照檔格式請用陣列而非物件，避免重複的 key 浪費體積。

## 5. 濫用防治

匿名 + 免審核 + 可放外部連結 = SEO 垃圾連結的完美載體。這個風險比洗版更高，
因為垃圾訊息有明確金錢動機。

- **Turnstile** — 對真人幾乎零摩擦，擋掉絕大多數 bot
- **網域白名單** — 只收社群平台與圖片託管網域，不在名單內直接拒收
- **`rel="nofollow"`** — 讓 SEO 垃圾失去動機，投報率最高的一招
- **說明欄位剝除所有 URL** — 連結只能走 `link` 欄位，否則白名單形同虛設
- **前端顯示網域而非完整 URL** — 避免字串偽裝
- **軟刪除後門** — 不用做完整後台，能讓我手動隱藏單一回報就好，用平台自帶的存取控制保護即可
- **快照保留數份歷史版本** — 被洗版時可快速回滾

## 6. 選點 UX

這是最容易做壞、且直接影響熱點分析品質的地方。

不要用 GPS 座標直接送出。流程應該是：

1. GPS 只用來把地圖移到大概位置
2. 地圖中心放**固定準心**，使用者拖動地圖對準樹
3. 強制 zoom 到足夠層級才允許送出
4. 疊上正射影像圖層，讓使用者能直接看到樹冠並對準

回報表單應該短。必填只有「位置」，其他全部可選——
降低門檻比蒐集完整欄位重要，因為熱點分析最需要的是**點的密度**。

## 7. 熱點分析（第一版之後）

第一版先把資料蒐集與呈現做好，但資料模型要為以下分析留路：

- 空間聚集偵測（同路段、同公園、一定半徑內的病樹計數）
- 可依證據來源切換門檻（例如「只看有公告的褐根病案例」）
- 加入時間維度，觀察是否從某個點向外擴散
- 「殘根未清」的點標為持續風險源
- 與受保護樹木圖層疊合，找出高風險的老樹群
- **沒有公告的移除**單獨成一層。這類點的空間聚集本身就是訊號

## 8. 定位與免責

這是**公民回報的存證專案**，不是官方診斷，也不做自己的因果判斷。
網站上要清楚寫明：

- 回報內容由使用者提供，位置與描述可能有誤
- 病因欄位是**現場公告或官方文件的記載**，不是本站的判斷
- 沒有公告的回報不代表移除不合法，只代表回報者當時沒看到公告
- 疑似罹病樹木應通報主管機關或請樹木醫師現場鑑定

措辭上呈現「此處的移除公告記載原因為捷運工程」，
而不是「捷運工程害死這棵樹」。這不只是禮貌問題——
以公告原文為準才是這個專案的資料價值所在，加油添醋反而會削弱它。

另外這一點請務必放在明顯的位置，不要只寫在說明頁深處：
褐根病造成根部與莖基部木材腐朽，樹木失去機械支撐後**可能在無風狀態下無預警自倒**，
這是褐根病之所以受重視的主因之一。
請提醒使用者不要靠近、攀爬或於疑似罹病的大樹下停留，回報時注意自身安全。

## 9. 待確認事項

實作前請先向我確認：

1. 技術選型你是否同意，有無更好的建議
2. 受保護樹木資料集的實際欄位與筆數，以及授權條款是否允許這樣使用
3. **台北市樹木移除公告的實際樣貌與法規依據**（這一項優先）：
   公告是否為法定必要程序、哪些情況才需要公告、公告上通常會寫哪些欄位、
   會貼多久。這會直接決定「病因」tag 的選項措辭與整個表單設計。
   請找幾張實際的公告照片來對照。
4. 承上，**是否有線上查詢管道**——例如樹木保護委員會的會議紀錄、
   公園處的移除案件清單。如果有，這可能是比使用者回報更好的資料來源，
   甚至可以像受保護樹木一樣 pre-seed，值得認真評估。
5. 褐根病的傳播機制與防治要點，請查證農業部林業試驗所、農業試驗所、
   農業知識入口網等權威來源。這部分現在只用於說明頁的科普內容，
   不再是回報判斷依據。已確認的兩點可以當基礎：
   - 主要傳染源是**罹病殘根**，傳播途徑為病根與健康根接觸、種苗帶菌、病土移動
   - 一旦地上部出現黃化萎凋，根部已有六成以上受害，俗稱「樹癌」
6. 圖磚與正射影像的免費來源
