## 1. 目的

建立一個公民回報的地圖網站，蒐集台北市**罹病與被移除的樹木**位置，
**核心目標是找出褐根病（Phellinus noxius）的空間熱點**，希望對防治有幫助。

這個目的必須貫串所有設計決策。這不是一個「樹木紀錄網站」，
而是一個**疫情地圖**。以下幾點都是從這個目的推導出來的。

### 為什麼熱點圖有價值

褐根病是藉病根傳播的真菌病害，主要透過**根系接觸**與**病根殘體的搬運**（含夾帶病根碎片的病土）擴散；
土壤本身不是病原的棲地，殘留的樹頭還可能長出子實體釋放孢子。
病死樹的殘根可在土中存活十年以上，持續作為感染源。
因此疫情高度**空間聚集**——同一路段、同一公園、同一校園的樹木會接續死亡。

現況是各單位（公園處、學校、里長、住戶）各自處理，沒有跨單位的空間視角。
一張公開的點位圖可以讓「這條街三年內死了七棵」這種模式浮現出來。

### 這個目的帶來的四個非顯而易見的設計要求

**(1) 病因必須有憑據，不要讓回報者自己判斷**

一般人無法、也不該判斷一棵樹為什麼生病或被移除。所以證據標準很簡單：

**以現場的移除公告或官方文件為準。** 台北市法規只要求修剪與移植施工前 3 到 7 日張貼告示，
移除前的現場公告是行政慣例而非法定義務（見 `RESEARCH.md` 第 1、2 節）。
有公告就照抄上面寫的；沒有公告是常態而非例外，病因留空，不要推測。

這條規則讓專案的性質改變，而且是往好的方向：

- 資料變成「官方自己說的」，不需要任何專業判斷就能達到高可信度
- 熱點圖上標為褐根病的點有文件依據，拿去跟公部門或里鄰溝通站得住腳
- 迴避了法律與爭議風險（見第 8 節）

代價是資料量會變少——很多樹是默默被移除的，或等有人注意到時公告早就撤了。
所以**必須允許「樹不見了但沒有公告」這種回報**：病因留空，點位照樣收。
而且要注意：大量沒有公告的移除聚集在同一區，本身就是值得注意的訊號，
不要把這類回報當成次等資料。

**(2) 照片連結的用途是存證**

`link` 欄位（Threads / IG / X 等貼文網址）是這個專案的核心，因為現場會消失——
公告會被撤掉、樹會被移走、樹穴會被填平，但網路貼文會留著。

引導使用者拍**三類照片**，都重要，而且可以放在同一篇貼文裡：

| 拍什麼 | 支持哪個欄位 |
|---|---|
| **移除公告** | 病因。這是唯一能決定病因欄位的憑據 |
| **樹木本體**（含樹幹基部、露出的根部、樹冠狀況） | 現況記錄。罹病或衰弱的樣貌、移除前後的對照 |
| **樹穴與殘株** | 處置。殘根還在不在、是否已水泥填平，只有這類照片看得出來 |

請注意這個分工：照片是用來**佐證使用者填的欄位**，不是用來讓使用者
從照片上自行判斷病因。病因永遠只看公告，見 (1)。

實務上很多情況只拍得到其中一類（例如發現時樹已經沒了，只剩樹穴），
這完全沒問題，UI 不要把附照片做成必填或多階段流程。

**(3) 殘根的去留有防疫意義**

使用者列的處置 tag（僅剩根部 / 連根移除 / 樹穴水泥填平）看起來像流水帳，
但在褐根病的脈絡下是關鍵資訊：**殘根留在原地 = 感染源留在原地**。
「已移除但殘根未清」的點應該被標示為持續風險，而不是結案。
「樹穴水泥填平」同樣不算結案：水泥不會殺死可存活十年以上的殘根，官方防治文件沒有任何一份支持這種處置，
鋪設水泥反而被列為誘發因子。說明頁應將其標為「未依官方建議處置」。

**(4) 定位精度比一般回報地圖更重要**

熱點分析靠的是空間鄰近性。手機 GPS 在台北市區誤差 10–30 公尺，
足以讓相鄰兩棵樹的相對關係錯亂。選點 UX 必須處理這件事（見第 6 節）。

## 2. 範圍與非目標

**做**
- 匿名回報、免審核、直接上線
- 地圖呈現 + tag 篩選
- 受保護樹木參考圖層（pre-seed）
- 官方解列紀錄層：從文化局樹保會議程 PDF 抽「受保護樹木需解除列管案件」表，join 受保護樹木座標後 pre-seed，之後定期爬
- 清冊消失訊號層：每日快照公園處行道樹清冊，diff 出消失的樹籤編號，標為「官方清冊中消失，原因不明」。先離線跑數週觀察誤判率再決定是否上線
- Turnstile 防機器人 + 連結網域白名單 + 我自己的軟刪除後門

**不做（第一版）**
- 使用者登入
- 審核流程
- 檢舉、重複回報合併、狀態更新機制 —— 保留資料模型的擴充空間，但先不實作
- IP 限流 —— 熱心回報者不該被擋，真的遇到惡意流量再處理
- 圖片上傳與託管 —— 一律走外部連結

**地理範圍**：不需要嚴格的行政區界。一個寬鬆方框即可——
跑到新北照樣收，跑到新竹才拒絕。不要為此引入行政區 polygon 與 point-in-polygon 判斷。

## 3. 資料模型方向

分成兩張**性質完全不同**的表，不要混在一起：

### `trees` — 參考圖層（唯讀）

來源：台北市資料大平臺的「臺北市受保護樹木」資料集（提供機關為文化局，
含樹木編號、樹種、胸徑、地址、經緯度等）。請自行確認目前的資料集 ID 與欄位。

**這些樹並不是病樹**。它們是老樹、大樹，是褐根病最重要的受害對象，
所以作為底圖參考有價值——但絕對不能 pre-seed 進回報表，
否則一上線就有幾千個假的「病樹」點，整個資料集失去意義。

視覺上應與回報點明確區分（例如灰色小點 vs 彩色標記）。
回報時若位置貼近某棵受保護樹木，應提示使用者關聯過去
（「這棵受保護樹木被移除了」是這個網站最有價值的一類回報）。

資料集現況（2026-09-18 查證，細節見 `RESEARCH.md` 第 4 節）：3,874 筆、13 個欄位，
授權為政府資料開放授權條款第 1 版，允許改作與商業利用，網站頁尾須顯名。
座標只有 4 位小數（約 11 公尺），沒有列管日期與狀態欄，解列的樹會直接從資料集消失。因此：

- 同步時要自己保留歷史：上次有、這次沒有的樹標為「疑似解列」，並嘗試對到樹保會解除列管紀錄
- 匯入時處理 2 筆緯度壞值（編號 2303、3213）與 1,057 筆地理位置名稱空白
- 「貼近某棵受保護樹木」的鄰近半徑以 15 到 20 公尺起算，並以樹種一致作輔助判斷

### `reports` — 使用者回報

欄位意圖（不是最終 schema，請自行設計）：

| 欄位 | 用途 |
|---|---|
| 座標 | 精度到小數第 5 位就夠（約 1 公尺） |
| 樹種 | **自由填寫文字**，不做 tag。可提供 autocomplete 建議清單輔助，但不限制輸入 |
| 病因 tag | 多選。**僅在有公告或官方文件憑據時填寫**，無憑據留空 |
| 處置 tag | 多選 |
| 證據來源 | 單選，見第 1 節 (1) |
| 資料來源 | 單選：使用者回報 / 樹保會解除列管紀錄 / 公園處移除計畫書 / 清冊消失偵測。讓熱點分析可以只看官方紀錄或只看回報 |
| 說明 | 自由文字，上限約 300 字。可用來照抄公告全文 |
| 連結 | 單一 URL，網域白名單 |
| 發現日期 | **可選，且與回報時間分開**。使用者常在事後才回報，擴散分析需要的是發現時間 |
| 關聯受保護樹木 | 可選，指向 `trees` |
| 狀態 | 供軟刪除使用 |
| 回報者識別 | IP 雜湊（加 salt，不存原始 IP）。不用來限流，只在遇到惡意流量時備用 |

### Tag 方向

三個 tag 維度加一個資料來源欄位，不要混成一組：

- **病因**（多選）：褐根病、病蟲害（褐根病以外）、腐朽／樹洞、枯死／自然死亡、
  傾倒風險／公共安全、風險評估高風險、竄根／破壞路面、車輛撞損、不明，以及**非病害原因**——
  捷運工程、道路工程、建築工程、公園整建／校舍工程、防颱修剪／颱風倒伏。
  非病害原因也要收，因為工程移除本身會移動病土、造成根系損傷，是褐根病的風險因子。
  措辭依實際公告、計畫書與作業要點的用語定案（頻率表見 `RESEARCH.md` 2.3、對照表見 8.6），
  讓使用者可以直接對照著選。

- **處置**（多選）：僅修枝葉、僅剩主幹、僅剩根部、連根移除、已移植、樹穴水泥填平、原地保留。
  注意第 1 節 (3) 的防疫含義：殘根留在原地就是感染源留在原地；
  「僅剩主幹」「僅剩根部」「樹穴水泥填平」在平地人工環境都屬未完成處置，說明頁要寫明。
  這一組的憑據是樹穴與殘株照片，見第 1 節 (2)。

- **證據來源**（單選）：
  現場公告（有拍到照片）/ 現場公告（沒拍到）/ 機關官網公告或計畫書 / 新聞報導 /
  高風險掛牌（尚未移除）/ 無公告，僅目擊。
  **預設為「無公告，僅目擊」**：法規上移除本來就不必現場公告，這才是多數情境。
  「機關官網公告或計畫書」是法定公開文件且每株有樹籤編號，可信度高於新聞轉述，所以與「新聞報導」拆開。
  這一項取代了原本的「診斷可信度」，理由見第 1 節 (1)。
  病因 tag 應該只在有憑據時填寫；「無公告，僅目擊」與「高風險掛牌」的回報預設病因留空。
  UI 說明要寫明：樹上的紅白警示帶是安全提醒，不是移除公告；高風險掛牌代表即將評估，不代表已決定移除。

- **資料來源**（單選，非 tag，系統或匯入程序填寫）：
  使用者回報 / 樹保會解除列管紀錄 / 公園處移除計畫書 / 清冊消失偵測。
  用途是讓熱點分析可以「只看官方紀錄」「只看使用者回報」切換。

tag 清單要放在**單一 source of truth 檔案**，前後端共用。
內部編號只能新增、永不重排或回收，否則舊資料的語意會錯亂。

## 4. 技術方向

「免費、方便、不要因為沒流量就被停用」是選型的唯一標準。
採 Cloudflare 全家桶（Workers Static Assets + Workers + D1 + KV + Turnstile），
理由是一個帳號搞定全部、免費額度夠用、且官方文件查不到任何閒置暫停條款
（Supabase 免費專案閒置一週會被暫停並需要冷啟動，不適合初期沒流量的公開站；額度數字與來源見 `RESEARCH.md` 第 7 節）。

兩個與常見組合不同的選擇：

- **不用 Pages，用 Workers Static Assets**：Cloudflare 官方已建議新專案用 Workers，且只有 Workers 有 Cron Triggers，
  前端、寫入、定時快照可以是同一個部署單位。代價是 custom domain 必須由 Cloudflare 託管 DNS。
- **不用 R2，用 KV 存快照**：R2 是整套裡唯一要走 checkout 綁付款方式的元件。KV 免綁卡，單值上限 25 MiB 放得下一萬筆快照，
  每天 1,000 次寫入允許每 2 分鐘 dump 一次。代價是讀快照要經過 Worker，用 `Cache-Control` 讓邊緣快取吸收重複讀取。
  流量成長到接近每天 10 萬次再搬 R2。

若你評估後有更好的組合，提出來討論。

地圖前端建議 MapLibre GL JS（避開 Google Maps 計費）+ client-side clustering。

圖磚定案（見 `RESEARCH.md` 第 5 節）：

- 底圖：國土測繪中心 WMTS（`EMAP`，或灰階 `EMAP01` 讓回報點更突出），EPSG:3857，免申請免金鑰，須註明出處
- 正射：臺北市都發局歷史圖資 WMTS 的 `Image_3857`（目前為 2025 年航照），備援 NLSC `PHOTO2`。
  都發局「不得對外流通發布予第三方」條款對公開網站 hotlink 是灰色地帶，上線前寄信確認；未確認前用 PHOTO2
- 不要預先抓政府圖磚自架（都發局明文禁止重製）。若要不依賴政府服務的穩定底圖，切 Protomaps PMTiles 台北範圖放 R2，那時才需要開 R2
- attribution 一次寫齊：國土測繪中心、臺北市都發局、臺北市文化局（受保護樹木資料）

### 一個必須遵守的架構原則：讀寫分離

不要讓使用者的讀取請求直接打資料庫。

```
寫入：使用者 → Worker（驗證）→ DB
讀取：Cron → DB 全表 dump → 產生靜態快照檔 → 寫入 KV（保留數份歷史版本）
      使用者 → Worker 從 KV 取快照並附 Cache-Control → 邊緣快取吸收重複讀取，完全不碰 DB
```

**「Worker」** 指 Cloudflare Workers，也就是跑在邊緣節點的 serverless function。
在這個架構裡它是唯一的後端，同一個 Worker 專案三條路徑：處理寫入請求、跑定時快照、從 KV 回傳快照。
沒有常駐伺服器、沒有容器、沒有部署主機要顧。

**「驗證」** 指寫入前必須在伺服器端做完的檢查，至少包含：

- Turnstile token 驗證（向 Cloudflare 驗，不是只看前端有沒有過）
- 座標落在寬鬆方框內（見第 2 節）
- `link` 的網域在白名單內，且是合法 URL
- 說明欄位剝除所有 URL、限制長度
- tag 值在合法範圍內
- 產生回報者識別用的 IP 雜湊

**這些檢查全部要在 Worker 做，前端的同等檢查只算 UX 輔助。**
前端驗證是為了讓使用者即時看到錯誤，不構成任何防護——
任何人都可以直接對 API 發請求，繞過整個網頁。

這件事講明是因為前端已經會做座標範圍與網域白名單的檢查，
容易讓人覺得後端重做一次是多餘的。不是多餘，是唯一真正生效的那一層。

理由：
- 資料量小（預估上限一萬點），全量快照壓縮後只有幾百 KB，一次載入即可
- D1 免費額度是按「引擎掃過的列數」計算，且自 2026/9 起超額查詢直接失敗；
  讀取走靜態檔可以讓這個風險趨近於零
- 資料庫額度用光時，網站還是看得到

快照檔格式請用陣列而非物件，避免重複的 key 浪費體積。
快照歷史版本用不同 key 保留（如 `snapshot:latest`、`snapshot:<timestamp>`），對應第 5 節的回滾需求。

兩個上線前要實測或另行安排的點：

- Workers Free 的 10 ms CPU 上限也套用在 Cron，把一萬筆序列化成 JSON 可能貼近上限。不行就分批，或升 Paid（USD 5/月，同時解掉 D1 超額硬失敗的擔憂）
- 公園處清冊 diff（每日下載 11 MB CSV、比對 9 萬筆）超出 Worker CPU 上限，這支 job 跑本機排程，結果再寫進 D1

## 5. 濫用防治

匿名 + 免審核 + 可放外部連結 = SEO 垃圾連結的完美載體。這個風險比洗版更高，
因為垃圾訊息有明確金錢動機。

- **Turnstile** — 對真人幾乎零摩擦，擋掉絕大多數 bot
- **網域白名單** — 只收社群平台與圖片託管網域，不在名單內直接拒收
- **`rel="nofollow"`** — 讓 SEO 垃圾失去動機，投報率最高的一招
- **說明欄位剝除所有 URL** — 連結只能走 `link` 欄位，否則白名單形同虛設
- **前端顯示網域而非完整 URL** — 避免字串偽裝
- **軟刪除後門** — 不用做完整後台，能讓我手動隱藏單一回報就好，用平台自帶的存取控制保護即可
- **快照保留數份歷史版本** — 被洗版時可快速回滾

## 6. 選點 UX

這是最容易做壞、且直接影響熱點分析品質的地方。

不要用 GPS 座標直接送出。流程應該是：

1. GPS 只用來把地圖移到大概位置
2. 地圖中心放**固定準心**，使用者拖動地圖對準樹
3. 強制 zoom 到足夠層級才允許送出
4. 疊上正射影像圖層，讓使用者能直接看到樹冠並對準（都發局 2025 年航照解析度足以辨識單株樹冠）

回報表單應該短。必填只有「位置」，其他全部可選——
降低門檻比蒐集完整欄位重要，因為熱點分析最需要的是**點的密度**。

## 7. 熱點分析（第一版之後）

第一版先把資料蒐集與呈現做好，但資料模型要為以下分析留路：

- 空間聚集偵測（同路段、同公園、一定半徑內的病樹計數）
- 可依證據來源切換門檻（例如「只看有公告的褐根病案例」）
- 加入時間維度，觀察是否從某個點向外擴散
- 「殘根未清」的點標為持續風險源
- 與受保護樹木圖層疊合，找出高風險的老樹群
- **沒有公告的移除**單獨成一層。這類點的空間聚集本身就是訊號
- **官方清冊中消失但無回報**的點單獨成一層，來自公園處行道樹清冊每日快照 diff
- 可依資料來源切換：只看官方解列紀錄／只看使用者回報

## 8. 定位與免責

這是**公民回報的存證專案**，不是官方診斷，也不做自己的因果判斷。
網站上要清楚寫明：

- 回報內容由使用者提供，位置與描述可能有誤
- 病因欄位是**現場公告或官方文件的記載**，不是本站的判斷
- 台北市法規並不要求移除前在現場張貼公告，沒有公告的回報不代表移除不合法，只代表回報者當時沒看到公告。
  這句要放在顯眼位置，不只寫在免責條款深處
- 疑似罹病樹木應通報主管機關或請樹木醫師現場鑑定

措辭上呈現「此處的移除公告記載原因為捷運工程」，
而不是「捷運工程害死這棵樹」。這不只是禮貌問題——
以公告原文為準才是這個專案的資料價值所在，加油添醋反而會削弱它。

另外這一點請務必放在明顯的位置，不要只寫在說明頁深處：
褐根病造成根部與莖基部木材腐朽，樹木失去機械支撐後**可能在無風狀態下無預警自倒**，
這是褐根病之所以受重視的主因之一。
請提醒使用者不要靠近、攀爬或於疑似罹病的大樹下停留，回報時注意自身安全。
警語可直接引用權威來源的原文（臺東區農改場「褐根病常造成大樹或老樹無風自倒」、
臺北市大地工程處手冊「根部木材腐朽而外觀常不易察覺，一遇強風豪雨則易無預警傾倒」）。

說明頁另外三點：

- 放林業試驗所林木疫情鑑定與資訊中心的診斷窗口（電話、信箱見 `RESEARCH.md` 6.10），這是「疑似罹病樹木應通報主管機關」的具體出口
- 防治藥劑寫「目前沒有針對褐根病正式登記的殺菌劑」；不要寫氰氮化鈣、太陽能消毒、待克利，這三者在權威文件中查無出處
- 病原學名寫 *Phellinus noxius*，並註明國際新名 *Pyrrhoderma noxium*，台灣官方文件沿用舊名
